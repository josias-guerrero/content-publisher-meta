# Deauthorization and data deletion

Provider callbacks accept JSON or form-encoded `signed_request`. HMAC-SHA256 is checked with the corresponding app secret before trusting identity; this is distinct from X-Hub-Signature-256. Mapping uses provider, app ID and the authorizing subject ID. The signed `issued_at` is a cutoff: replaying an old callback does not revoke an authorization created later. Repeated deletion requests with the same subject/cutoff reuse the confirmation; later requests have independent confirmations. Public status contains only status and is no-store.

A valid request is appended and fsynced to an independent signed journal **before acknowledgment**. It revokes matching connections and cancels pending work. In-flight work must be reconciled before erasure; it is never silently reposted. A pending request blocks new OAuth for that subject. Publisher outbox announces the exact affected post IDs by agency/client; large scopes use 500-ID batches and a digest of the complete scope. Tiko persists signed events and requires all batches before building a plan. No remote Meta publication is deleted by this workflow.

## Independent journals

Production requires publisher `DELETION_LEDGER_PATH` / `DELETION_LEDGER_SECRET`, plus Tiko `TIKO_DELETION_LEDGER_PATH` / `TIKO_DELETION_LEDGER_SECRET`. Initialize each once with its `scripts/init-deletion-ledger` command; the parent directory must already exist. Use a private file (0600) in a **separate persistent recovery volume**, independently replicated and access-controlled. Never include that volume in a SQLite/uploads rollback. The startup replay happens before listening or running publisher jobs. Missing, malformed, incomplete or incorrectly signed journals fail startup. Preserve the signing keys; rotating them requires re-signing and verifying the full journal in maintenance.

Journals contain internal IDs, scoped subject hashes, filenames and minimal backup/receipt evidence, never access tokens or captions. They are still sensitive and need an approved retention policy. Signatures detect alteration; they cannot detect an operator deliberately replacing the entire journal with an older valid copy. Independent custody/replication and restore procedures are necessary. Do not initialize an empty journal to bypass a failed restore.

## Reviewable operator workflow

Use the staging rehearsal in [guia-pruebas.md](guia-pruebas.md) first. These commands require the intended service environment and explicitly selected databases; never run them on production as an experiment.

1. Publisher: `./node_modules/.bin/tsx scripts/process-deletion.ts REQUEST_ID` prints a dry-run scope. Resolve `publishing` / `reconciling` outcomes without republishing. Allow the outbox to deliver every deletion batch to Tiko.
2. Stop the Tiko HTTP process for a maintenance window; keep publisher accessible for read-only status checks. Set `TIKO_MAINTENANCE_DB` and `TIKO_MAINTENANCE_UPLOADS` to the intended existing staging paths. In the Tiko repository run `node scripts/publisher-deletion.js plan REQUEST_ID AGENCY_ID CLIENT_ID /tmp/approved-scope.json`. This writes a new private manifest. Review item IDs, exclusive media, preserved shared media, Drive IDs and leases. Unknown/mismatched ownership blocks the operation; do not guess it.
3. Create an evidence JSON with four nonempty strings: `snapshots`, `offsite`, `drive`, `shared`. Record actual dispositions and independently owned shared-file exclusions, including backup copies made by `lib/respaldo.js`, imported Drive originals, provider snapshots and exports. For a synthetic empty staging environment, explicitly record that none exist. This is an operator attestation: the script does not access or erase third-party backup services. Retained backups must remain inaccessible to ordinary users and subject to the documented expiration/restore filters. Obtain the appropriate scope/retention decision before erasing them.
4. In Tiko run `node scripts/publisher-deletion.js apply REQUEST_ID AGENCY_ID CLIENT_ID /tmp/approved-scope.json /tmp/backup-evidence.json`. It rechecks the current manifest and asks publisher for authoritative terminal states. It journals the approved plan before mutating local data, scrubs linked pieces/logs/intents/permalinks, revokes affected media leases, and removes exclusive originals and derived thumbnails/covers/frames. Media referenced by other pieces/intents/client photos is preserved. It writes `/tmp/approved-scope.json.receipt.json`, an array containing a signed receipt for this scope. Repeat for each affected agency/client.
5. If interrupted, restart in maintenance and replay the independent journal. `node scripts/publisher-deletion.js receipt REQUEST_ID AGENCY_ID CLIENT_ID /tmp/recovered-receipt.json` replays unfinished local erasure and exports the persisted receipt. It never signs a new completion without having applied the approved erasure plan. Combine per-scope receipt objects into one JSON array if multiple scopes are involved.
6. Publisher: `./node_modules/.bin/tsx scripts/process-deletion.ts REQUEST_ID /tmp/tiko-receipts.json 'REFERENCE_TO_PUBLISHER_BACKUP_DISPOSITION'`. Every scope must have a valid shared-secret signature and exact post-set digest. A plain boolean flag no longer suffices. The publisher independently checks in-flight work, journals completion, scrubs tokens/content/OAuth payloads and relevant historical outbox payloads, and retains minimal terminal IDs/idempotency hashes. It emits completion and changes public status to `completed`. A retry is idempotent.
7. Restart Tiko and verify public deletion status, exclusive/shared media, other subjects and the restore scenario below. Archive only minimal evidence in a restricted location; dispose of temporary manifests/receipt exports according to approved retention.

`completed` means the approved active scope was processed and signed operator evidence covers external disposition. It is not a provider-confirmed assertion that every third-party backup byte vanished. Legacy requests accepted before migration 6 without an exact scope stop for explicit reconstruction. Legacy Tiko records without verified publisher links also stop; migrate/reconcile before claiming completion.

## Restore rehearsal

Take a consistent staging backup before deletion. After completion restore **only** SQLite/uploads; keep the current independent journals and keys. Start publisher and Tiko with workers off. Publisher reapplies revocation/erasure to the restored authorizations/posts; Tiko reapplies item/media cleanup and receipts before serving. Check exclusive files and derivatives are absent, shared assets survive, old pending jobs cannot execute, and the public code still reports completed. A restored in-flight job covered by a completed erasure becomes cancelled locally, without making any claim about historical remote content. Test missing/tampered journals with disposable copies: neither service should start.
